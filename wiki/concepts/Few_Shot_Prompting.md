## 定義

Few-Shot Prompting（少樣本提示）是一種通過向語言模型提供少量（通常 2-5 個）示例來引導模型理解任務模式和期望輸出格式的技術。與 Zero-Shot（無示例）相比，Few-Shot 能顯著提升輸出的一致性和準確性。

核心思想：展示，而非僅僅是告訴（Show, don't just tell）。

## 為什麼有效

1. **模式識別**：LLM 能夠從示例中識別輸入-輸出對映模式
2. **格式引導**：示例直觀展示期望的輸出格式和結構
3. **上下文學習**：無需微調，模型在推理時從示例"學習"任務
4. **減少歧義**：消除對指令的不同解讀可能性

## 示例數量

### 推薦範圍
- **3-5 個示例**：大多數場景的最佳選擇（Anthropic 推薦）
- **1 個示例 (One-Shot)**：簡單任務或 token 受限場景
- **更多示例**：複雜任務，但要注意輸入長度限制

### 數量權衡
- **過少**：可能不足以展示模式全貌
- **過多**：
  - 增加 token 成本
  - 可能導致模型對示例"過擬合"
  - 可能觸發模型的「最近示例偏見」

## 示例品質原則

### 1. 相關性
示例應儘可能接近實際使用場景。

```
❌ 不佳：用郵件分類示例來訓練產品描述生成
✅ 良好：用類似產品的描述作為示例
```

### 2. 多樣性
覆蓋不同的邊緣情況和變化。

```
任務：將產品描述轉為社交媒體帖子

示例 1：消費電子（耳機）
示例 2：食品飲料（咖啡）  
示例 3：傢俱（辦公椅）
示例 4：邊緣案例（超長描述）
```

### 3. 格式一致性
所有示例使用相同的格式、分隔符和結構。

```
任務：將訂單解析為 JSON

示例 1：
訂單：一份芝士漢堡和薯條
輸出：
```json
{
  "cheeseburger": 1,
  "fries": 1
}
```

示例 2：
訂單：兩份漢堡、一杯飲料和薯條
輸出：
```json
{
  "hamburger": 2,
  "drink": 1,
  "fries": 1
}
```
```

### 4. 高品質
示例本身必須是正確的、清晰的。

> "一個小的錯誤都可能讓模型困惑，產生不期望的輸出。" —— Google 白皮書

## 格式技巧

### 使用標籤包裹
Anthropic 推薦使用 XML 標籤明確標記示例：

```
<examples>
<example>
輸入：[輸入內容]
輸出：[期望輸出]
</example>

<example>
輸入：[輸入內容]
輸出：[期望輸出]
</example>
</examples>

現在，請處理以下輸入：
輸入：[實際輸入]
輸出：
```

### 明確輸入/輸出分隔
使用清晰的分隔符，如 `"""`、`###`、或特定標籤。

## 與 Zero-Shot 對比

| 維度 | Zero-Shot | Few-Shot |
|------|-----------|----------|
| **適用場景** | 簡單、明確定義的任務 | 特定格式、風格或模式要求 |
| **Token 成本** | 低 | 中（取決於示例長度） |
| **一致性** | 中等 | 高 |
| **靈活性** | 高 | 受示例限制 |
| **設定時間** | 快 | 需要準備優質示例 |

## 特殊考慮

### 分類任務的類別混合
對於分類任務，確保示例覆蓋所有類別，避免類別偏見：

```
❌ 不佳：所有示例都是 "積極" 情緒
✅ 良好：積極、消極、中性示例均衡分佈
```

### 當示例足夠清晰時
Google 和 Anthropic 都指出：

> "如果你的示例足夠清晰地展示了當前任務，你甚至可以移除指令。"

在這種情況下，Few-Shot 本身就能指導模型行為。

## 常見錯誤

1. **示例與任務不匹配**：示例太通用或與實際情況差異大
2. **格式不一致**：示例之間使用不同的分隔符或結構
3. **示例品質差**：示例本身有誤或模糊
4. **忽略邊緣情況**：所有示例都是"典型"情況
5. **過度依賴示例**：示例中引入不需要的偏見或限制

## 最佳實踐總結

1. **始終使用示例**：除非任務極其簡單，否則建議包含 3-5 個示例
2. **多樣化示例**：覆蓋不同場景和邊緣情況
3. **保持格式一致**：使用標籤和分隔符保持一致性
4. **驗證示例品質**：確保示例本身正確無誤
5. **考慮 token 預算**：示例會增加輸入成本，權衡品質與成本
